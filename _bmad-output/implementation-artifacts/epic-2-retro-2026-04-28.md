## What Went Well

1. **Plugin encapsulation held up end-to-end.** `fastify-plugin`'s `fp()` wrapper was correctly applied in all three plugins — no scoping bugs, no decorator leakage. The `fastify.db` decorator was visible in all routes without any issues.

2. **Repository pattern enforced a clean boundary.** All SQL lives exclusively in `TaskRepository.ts`. Routes, plugins, and tests never touch SQL strings. The `snake_case → camelCase` mapping stays in exactly one place, consistent with the project's language-specific rules.

3. **Error contract was airtight.** The triple — JSON Schema validation (AJV) → `@fastify/sensible` helpers → `errorHandler.ts` — means no route can accidentally leak internal details. NFR7 and NFR8 satisfied completely.

4. **Test design was appropriately layered.** In-memory SQLite for `TaskRepository` integration tests; mock module (`mock.module()`) for route unit tests. Two isolation strategies, each right for its layer. 21 tests, zero I/O latency from real DB.

5. **Deferred-work log discipline improved** vs Epic 1 — 13 items, all with reasons and context.

6. **Autoload discovery worked cleanly.** Three new plugins and one new route file were discovered by `@fastify/autoload` without modifying `app.ts`.

## What Didn't Go Well

1. **Architecture document `server/src/` path assumption.** Every one of the four Epic 2 stories required a 'CRITICAL: server has no `src/` subdirectory' dev note to correct the same stale assumption. This is compounding friction — each story agent had to re-discover the same problem independently rather than it being fixed at the source.

2. **`noEmit: true` build constraint unresolved.** The project cannot produce a compiled production build via `tsc` because `.ts` import extensions require `allowImportingTsExtensions` which forces `noEmit`. Local development and CI tests work fine, but a compiled server artifact for Railway deployment does not exist. This is a gap heading into Epic 4.

3. **`Task.userId` discrepancy between architecture doc and implementation.** `shared/types.ts` includes `userId: number | null` in the `Task` interface, but the architecture document's specification does not reflect this. Story 2.2's dev notes had to call it out explicitly.

4. **`--experimental-test-module-mocks` flag dependency.** Route tests rely on an experimental Node.js flag. This works today but carries stability risk on Node.js version upgrades.

## Root Cause

The primary challenge shares the same root cause as Epic 1: **assumptions encoded in planning documents, not updated when implementation diverges.** The `server/src/` path correction was known after Story 1.3 but never propagated back to `architecture.md`. The `userId` addition to `Task` was implemented but not reflected in the architecture doc.

## Key Insights

1. Story dev notes are a reliable signal for upstream doc rot — when every story in an epic has the same 'CRITICAL' correction, that correction belongs in the source document, not repeated in each story.
2. The REST API layer (Epic 2) is fully operational and provides a solid, tested foundation for Epic 3 frontend work. No architectural assumptions were proven wrong.
3. Build toolchain decisions (production compilation strategy) need to be explicit before deployment epic begins — not discovered at deploy time.
